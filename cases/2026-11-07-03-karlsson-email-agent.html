让智能体每天两次整理邮箱：8 次采样每 run 归档约 17 封

作者/出处：Emil Ingemar Karlsson
原文：https://www.emilingemarkarlsson.com/blog/ai-email-agent-zero-inbox-calendar-digest
日期：2026-11-02 · 工具：Grok Bot 定时任务、 Gmail、 Google Calendar
成本：无服务器、无代码；Grok 定时任务的订阅档位价原文未给，复现前须自行核对 · 耗时：约 30 分钟上手（写一套分拣规则 + 设两个定时任务）

一句话

不用写一行代码：两条 Grok 定时任务每天 05:00 与 19:00 各跑一次，按一套 plain language 的规则读 Gmail、分拣归档、看日历，发一条短摘要——作者从 2026 年 9 月起就没再手动分过一封简报，8 次采样里每 run 平均归档约 17 封。

原作者怎么做的

  1. 先写“禁令清单”，再写“能做什么”：智能体永不发送、永不删除、永不擅自起草；唯一例外是一个已知的骚扰发件人，直接丢弃。所有对外动作都要人先批准。
  2. 设两个定时任务：早上约 05:00 与晚上 19:00（斯德哥尔摩时间），同一套规则；晚上的任务只处理早上之后新到的邮件；无服务器、无自己的 cron。
  3. 分拣规则故意写得很“无聊”，只有五条：需要回复的进 Action/Reply、留收件箱；涉及账单或付款的进 Action/Payment、留收件箱；简报与更新类打标签归档（收据、续费、服务通知仍可搜索，重要的在摘要里提一行）；其余全部打 Processed 标签归档；反复出现的邀请自动加到对应的共享日历（不邀请任何人）。
  4. 每天两份摘要，固定四段：需要你处理的（通常 3–5 个 thread，每条一句话说明对方要什么、下一步是什么）→ 已整理（归档了多少封、什么类型，值得知道的提一行，如域名续了、发票要自动扣款）→ 未来两周日历 → 待跟进的 open loop（如约好了但还没订的会）。什么都没变的日子，摘要只有两行——安静的日子只花十秒。
  5. 需要回复的 thread，作者用一句话告诉智能体想说什么（如“按事实回，带日期、谁等了谁、下一步”），智能体读完整条 thread、理出时间线、写成草稿；草稿以聊天卡片或 Gmail 草稿的形式出现，作者改两三轮、自己点发送。
  6. 数数：作者坚持“Count something”——每 run 归档多少封、剩下几个待办 thread，都是免费指标，让效果看得见。

结果

  • 实测（8 次采样）：每 run 归档 38、35、27、19、8、4、3、3 封，平均约 17 封；每次剩下 3–5 个需要作者处理的 thread（第一次大清理归档 64 封，未计入平均）
  • 省时（作者明标的估算，非实测）：每天约 34 封 × 每封 10–20 秒手动分拣 ≈ 6–11 分钟，加上每天约 5 分钟的日历检查，合计每天约 11–16 分钟、每周约 1.3–1.9 小时；作者在文中用表格逐项列出假设，并说明回草稿的时间因人而异、未计入
  • 运行状态：自 2026 年 9 月起持续运行；作者称不再“只是为了看一眼”而打开收件箱，真正的收益是更少的上下文切换，不只是分钟数

提示词结构

（按原文做法还原的任务骨架，非原文逐字提示词）

```

角色：[我的邮件分拣员 + 日历摘要员：只读、只归档、只起草，永不发送、永不删除]。

输入：[Gmail 新邮件] + [Google 日历] + [我在聊天里临时提的要求]。

禁令先行：[不发送、不删除、不擅自起草；唯一例外：已知骚扰发件人直接丢弃]。

分拣规则：[需回复 → Action/Reply，留收件箱] [账单/付款 → Action/Payment，留收件箱] [简报/更新 → 打标签归档，重要的在摘要里提一行] [其余 → Processed 标签归档] [反复出现的邀请 → 加到对应共享日历，不邀请任何人]。

摘要（每天 05:00 与 19:00 各一次，固定四段）：[需要你处理：3–5 个 thread，每条一句话（对方要什么 + 下一步）] [已整理：归档数与类型 + 值得知道的一行] [未来两周日历] [待跟进 open loop]；[无事发生时只写两行]。

回草稿：[我一句话说明想说什么 → 你读完整条 thread、理出时间线、写成可编辑草稿]；[我改完、我点发送]。

计数：[每 run 记录归档数与剩余 thread 数]。

```

中国读者怎么迁移

这套做法的精髓是“禁令先行 + 固定时间两次摘要 + 数数”，工具可以平替：Grok 定时任务在国内访问与订阅方式不同，可换成 Claude 的定时任务、ChatGPT Tasks 或其他支持定时 + 邮箱/日历连接的智能体；Gmail 换成自己的邮箱，日历同理。分拣规则本身是纯文本，五条规则照抄即可；“安静的日子只写两行”是防打扰的关键设计，不要省。作者在瑞典用瑞典语收摘要，语言不影响结构。

风险与限制

  • 结果口径：归档数是 8 次采样的实测，但 1.3–1.9 小时/周是作者按“每封 10–20 秒 + 每天 5 分钟日历检查”算出的估算，作者本人在文中明确区分了实测与估算，成稿照录，不得写成实测省时。
  • 成本口径：原文只说“无服务器、无代码”，未给 Grok 定时任务的订阅档位与价格；成稿不写 $0，复现前须自行核对档位与价格。
  • 隐私口径：做法的前提是让智能体读全部邮件并打标签归档；敏感邮件、账单信息进智能体的上下文之前，先确认该服务的留存与训练政策；作者“禁令先行”的做法值得照抄。
  • 适用边界：规则基于作者个人的邮件结构（简报多、待办少）；收件箱以工作往来为主的读者，Action 类会远多于 3–5 个 thread，摘要会变长；定时任务的可靠性取决于平台本身，原文未给失败率。
  • 与已发布案例的边界：与已发布 2026-10-17-04 Fiverr 收件箱智能体不同任务（彼为自由职业者处理客户收件箱、按单赚钱，此为个人零收件箱 + 日历摘要、无代码定时任务）；与被淘汰的 Frank Massey 收件箱 30 天不同（彼正文含未填占位符数字，此有 8 次采样实测）。
