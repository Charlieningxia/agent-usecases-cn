一句话

凌晨 3 点的告警从来不是 96 件事，而是 2 件事被吵了 96 遍：作者用本地模型 + 三阶段智能体跑了一套夜间告警基准，把 418 行日志压成 4 行摘要——但这只是基准演示，不是真实值班周，省 42 分钟是换算值，别当成已省下的工时。

原作者怎么做的

  1. 先定基准再谈省时：96 条夜间告警、418 行日志全部是同一套演示数据，不是某周真实值班记录；输出只认“簇 + 摘要 + 可执行补丁”，不认模型自夸。
  2. 三阶段串起来，不是一步到位：Google ADK 的 SequentialAgent 依次跑 NoiseFilter（去噪）→ SandboxPatch（沙箱里出补丁）→ TwoLineBrief（两行简报）；Pydantic v2 强 schema 卡住输出格式，Sentry Agent Tracing 留下每步轨迹。
  3. 每簇都给可验证的补丁证据：Redis 连接池耗尽簇（62 条/310 行）附 pytest 312.4ms、18 个断言；Pydantic webhook 枚举缺 refund_queued 簇（34 条/108 行）附 184.6ms；补丁一命令可提 PR（git apply … && gh pr create --fill）。
  4. 看板与复跑都留出口：FastAPI 看板（端口 8095）看簇与摘要；一命令 python scripts/run_slothsre_demo.py 可复跑整套基准；仓库开源（github.com/RobinaMirbahar/slothsre-napops）。

结果

  • 压缩：96 条告警、418 行 → 2 簇、4 行摘要，阅读量降 99.04%（仅测试未验证，基准演示）
  • 省时换算：作者自称每次夜班省 42 分钟人工翻日志（仅测试未验证，换算值，非生产实测）
  • 补丁证据：Redis 簇 pytest 312.4ms、18 个断言；webhook 簇 184.6ms（仅测试未验证，基准内数字）
  • 成本：开源免费；本地跑 Gemma 4 的硬件成本原文未给，$0 token 费不等于 $0 总成本

```

先给基准再给结论：[固定告警集：条数/行数] + [输出只认簇 + 摘要 + 补丁证据]，不拿演示数据报生产收益。

三阶段分工写死：[去噪：把重复告警并成簇] → [沙箱出补丁：补丁必须附测试耗时与断言数] → [两行简报：只写簇 + 动作]，每步留轨迹。

格式用 schema 卡住：[Pydantic 强类型] 约束簇结构与摘要行数，模型不能用一段散文蒙混过关。

补丁要能一命令提 PR：[git apply] + [gh pr create --fill]，提不出去的补丁不算数。

```

中国读者怎么迁移

值班、运维、跑定时任务的读者能直接抄两点：一是“先并簇再读”——夜里被告警吵醒时，先让脚本把重复告警并成簇、每簇只读一行摘要，而不是逐条翻；二是“补丁附证据”——每个簇的修复必须带测试耗时与断言数，否则只是换了个地方的猜测。注意：本地跑 27B 模型需要显卡与显存，个人电脑跑不动时可先只抄“并簇 + 两行简报”的结构、用小模型或规则脚本代替。

风险与限制

  • 基准演示不是生产：96 条告警是演示数据，非真实值班周；省 42 分钟是作者换算值，没有真实夜班对照；引用时必须带“仅测试未验证”。
  • 参赛稿背景：Hacktoberfest Week 3 参赛稿，演示完整度优先于生产鲁棒性；告警源、误报率、漏报率在基准外未给。
  • 硬件成本未给：本地 Gemma 4 的显卡、显存、电费都不在文中；照搬前先在自己机器上测一命令复跑的耗时与资源占用。
  • 与已淘汰项目区分：SlothSRE 与此前淘汰的 SlothTidier、SlothOps 是不同项目，勿混淆；与已发布 CI 安全扫描、欧盟黑箱扫描不同问题（本篇是告警压缩，不是扫描）。
