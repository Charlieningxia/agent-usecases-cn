一句话

智能体说“做完了”最不可信的时候，就是它说得最顺的时候：作者在一个 Kotlin 微服务单体仓里给 Stop 装了一道硬门禁——10 天里它跑 220 次、拦下 95 次，其中一晚连续拦 19 次；作者的结论是，每次都通过的门禁只是装饰，拦得比放行多的门禁才在干活。

原作者怎么做的

  1. 分清“建议”与“墙”：作者引用 Böckeler 的 harness 定义——指南（事前 steering：指令、模板、宪法）只是建议；传感器（事后反馈：编译器、lint、测试、拦截型 hook）才是墙；并引用 Anthropic 文档：CLAUDE.md 是 advisory，hook 给的是确定性控制。
  2. 立三道门禁（写进宪法第 8 条，feature 001 先建门禁再写业务）：

- 每文件门禁：每次 Write/Edit 后触发；Kotlin 跑 ktlint + detekt + 最多 20 个同名前缀测试类，TypeScript 跑 eslint + tsc + prettier + vitest related；预算 300 秒、报告上限 60 行，失败 exit 2 拦住智能体；

- Stop 门禁：智能体说 done 时触发，跑全仓 ./gradlew -q verify（check + 各域 Pitest + 前端 lint 测试 + 增量 Stryker），预算 1200 秒共享时钟，exit 2 = 不许停；

- PR 门禁：GitHub 上重跑 verify + 变异棘轮 +“PR 新增行上的存活变异必须在描述里说明”+ hook 自身测试套件，是分支保护唯一要求的状态。

  1. Stop hook 四条规则（作者说“最值得抄进任何项目”的是第四条）：

- 无相关变更 2 秒跳过（以 marker 文件比时间戳；10 天跳过 33 次）；

- 可 bypass 但留痕（HOOK_BYPASS=1 跳过一次、写 bypass.log；PR 模板强制填“Gate bypasses”一节，缺了 PR 门禁直接失败；10 天只用 1 次，理由还是排练）；

- 共享时钟跑完全部检查，超预算的检查记 TIMEOUT，不留后台进程；

- 绝不连续拦两次（stop_hook_active 为真时改以 systemMessage 呈现同一报告、exit 0 放行；平台本身 8 次连拦才兜底，作者收紧到 2 次；20 行 loop-guard 测试覆盖 4 种状态）。

  1. 输出格式也是需求：成功时静默（Gradle --quiet、只报 FAILED、npm loglevel=error）；失败时只给“门禁名 + 可粘贴的精确命令 + 每检查最多 40 行 + 被截行数”，因为读者是上下文有限、不能往上翻的模型。
  2. 给门禁本身写测试：23 个测试脚本 + 假 gradlew/npm/npx 的 fixture 单体仓，PR 门禁在独立小 runner 上跑；1349 行 shell 全过 shellcheck -S warning。

结果

  • Stop 门禁 220 次：放行 92、拦截 95、跳过 33（已实现，作者日志）
  • 10 月 3 日晚连续拦截 19 次（19:08 UTC 起至午夜后），作者当时大多没在看（已实现，作者日志）
  • 10 月 8 日起翻转：门面就位、测试套件稳定后，连续放行 19 次、每次约 5 分钟——门禁没变软，是代码变好了（已实现，作者日志）
  • 红 verdict 中位 142 秒 vs 绿 293 秒（Gradle 在首个失败模块即停；全通过必须跑全部模块）；10 天门禁总耗时 13.2 小时；每文件门禁每次 +47 秒（已实现，作者日志）
  • 每文件门禁 90 分位 50 秒（目标 60 秒内）；全门禁中位 293 秒、90 分位 515 秒（目标通常 15 分钟内）（已实现，作者日志）

中国读者怎么迁移

自己用 Claude Code / Codex 的读者，今天就能先抄最值钱的两件：一是 Stop 门禁的“绝不连续拦两次”（20 行测试脚本可直接仿写），二是“成功静默、失败 40 行”的输出格式——前者防智能体在“done—被拦—done”里空转，后者省上下文。Gradle/Kotlin 栈可换成自己的 npm test / pytest / go test，但三条要保留：跳过无变更、bypass 留痕且 PR 模板强制披露、共享时钟防后台残留。作者的提醒也要一并带上：门禁 10 天吃掉 13.2 小时，6 人团队感受会完全不同——先在个人仓跑一周、看拦截率再决定上不上团队。

风险与限制

  • 漏检数无法统计：作者自承“我能告诉你 Stop hook 拦了 95 次，但说不出它没拦住多少坏改动——没有这种日志”；拦截率高不等于覆盖率高，传感器从不触发也可能是瞎子。
  • 传感器本身是智能体写的测试：作者引用 Böckeler 的质疑——对 AI 生成的测试寄予厚望“还不够好”；他的对冲是变异测试（Part 3 主题），且自承“不是完整的答案”。
  • 每文件门禁数据不完整：日志里只有 24 行每文件记录、对不上几百次编辑，作者自承原因未找到（可能子智能体的 hook 输出没写进同一文件）；引用每文件数字时要带上这个缺口。
  • 成本是时间不是现金：13.2 小时跑在作者笔记本上；团队规模、机器性能、测试套件大小都会改这个数，不能直接抄。
  • 强绑定单一栈：门禁 tied to 一个仓库、Gradle、Claude Code 的 stop_hook_active 协议；作者自述一旦平台改协议、测试会报警、但仍得自己修。
  • 与已发布案例的边界：本站已有 Anthropic 代码审稿流水线（2026-10-20-02，审稿是“看代码”）与 CI token 分流；这篇是“拦住智能体说完成”的确定性门禁 + 10 天真实拦截日志，机制与证据都不同。
