让智能体当值班 DBA：灾难告警 5 分钟内发回带根因的报告

作者/出处：Renz Bagasbas
原文：https://renzbagasbas1130.wixsite.com/renzbagasbas/post/the-on-call-dba-that-never-logs-in
日期：2026-11-06 · 工具：Claude Code（headless）、 自研只读 SQL MCP（55 个工具）、 Slack、 Windows Scheduled Task、 PowerShell
成本：实测每 tick $0.22（静默）~$0.85（带诊断）；5 分钟频率下预算 $65–75/天；另需 SQL Server 集群、Slack、Windows 服务器（已有基础设施，不另计） · 耗时：读者照做需数天搭建（非一天上手；已有 SQL Server + Slack 的 DBA 团队可按 10 条规则复现）

一句话

值班 DBA 最烦的前半小时是固定的：告警一响，翻笔记本、连 VPN、跑同一批首查 SQL。作者把这半小时交给了一个只读的 headless Claude Code 监控——11 月 6 日早上一次真实灾难告警，4 分 46 秒后根因分析已经发到他的私信里，0 秒数据丢失。

原作者怎么做的

  1. 先有一台只读 SQL MCP 服务器（作者此前文章的成果）：55 个工具，全部建立在微软官方诊断面（DMV、Query Store、Extended Events、system_health、默认 trace、msdb 作业历史）之上；查询白名单只放行 SELECT / WITH / DECLARE，其余一律在到达 SQL Server 之前拒绝。
  2. 三层只读防线：登录账号本身只有读权限；连接串带 ApplicationIntent=ReadOnly，写操作在引擎层失败；MCP 白名单再拦一道。密钥不在磁盘上，存在 Windows Credential Manager，运行器读出来放进环境变量。
  3. 监控做成“tick”而非守护进程：每 5 分钟一个 Windows Scheduled Task，用 PowerShell 包一层 claude -p 跑一次；另有一个只负责监听的 Slack listener，告警到达 30 秒后触发一次 tick。每次 tick 从一个 JSON 状态文件读水位、写回水位，绝不重复处理同一条消息。
  4. 每条规则都写进代码而非提示词：严重度取告警文本里的第一个 CRITICAL/HIGH（DISASTER 与生产宕机强制算 CRITICAL）；能私信谁、能在哪个频道回帖，都在脚本里用正则和白名单硬编码，模型说服不了它。
  5. 每次 tick 固定做一次全队扫描：对 8 个节点跑 fan-out 查询，对照基线判断 Agent 是否运行、启动时间是否变了、10 分钟内是否新增 3 个以上 dump——因为一次崩溃会连告警本身一起带走（r3-db1 的 Agent 停了 22 分钟，它的告警就发不出来）。
  6. 报告格式固定、手机可读：一条加粗标题（严重度 + 节点 + 时间）、一句话影响、2–4 条“我们测到了什么”（带数字）、Who（节点、数据库、SPID、登录、主机）、Why（每条结论标 Measured / Inferred / Withdrawn）、Do（精确的 T-SQL 与执行人，或“Nothing to run”）、Watch（现行规则）。CRITICAL 不超过 3,500 字符。
  7. 报告前做两遍校验：结论是否成立（对照组、基线、正确的 SPID、单位）；再从另一个来源重测关键数字。查不到就写“not captured：为什么”，不猜。

结果

  • 2026-11-06 07:51 CRITICAL 告警（R3 可用性组切换角色），32 秒后基础设施监控追加 DISASTER（r3-db1 的 SQL Agent 宕机）；07:55:47 首份根因分析已到作者私信：r3-db1 崩溃、r3-db2 已是主节点、0 秒数据丢失、崩溃节点的 Agent 仍停着导致日志备份已停，并附两条修复命令；随后 24 秒内又来 4 条私信，每条告警各一条
  • 从 CRITICAL 发出到私信送达共 4 分 46 秒；作者把首份报告贴进事故线程 11 秒后，一位工程负责人回复：“Great report by AI agent at least 👏”
  • 事后复测：关键数字全部成立；监控还发现了自家告警程序的一个 bug（复制告警里的错误行来自告警查询本身，不是复制故障）
  • 诚实记录的短板：崩溃前半小时它把 r3-db1 的第一个 dump 评为 LOW（一个 dump、无重启、不成风暴），下一个 dump 就是致命的；08:12–08:19 它自己丢了 SQL 访问，如实上报、排队了三项检查，恢复后补跑；Agent 第二次停止时写明“who issued the stop：not captured”，并给出查 Windows 事件日志的命令而不是猜测
  • 成本实测：静默 tick 约 $0.22，带诊断最高 $0.85；5 分钟频率下预算 $65–75/天

提示词结构

（按原文 10 条规则还原的任务骨架，非原文逐字提示词）

```

角色：[值班 DBA 的首次响应，只读，永不写库、永不发帖、永不猜测]。

输入：[Slack #db-alerts 与 #infra-alerts 的新消息] + [状态文件：上次处理的水位、已知问题与 WATCH 规则、已回复线程]。

每 tick 先做：[全队扫描：8 个节点 fan-out 查询 Agent 状态、启动时间、dump 数，对照基线]。

再处理新告警：[严重度取告警文本第一个 CRITICAL/HIGH；DISASTER 与生产宕机强制 CRITICAL] → [用只读工具查：谁在跑、谁阻塞谁、计划是否变了、在等什么、AG 是否健康、是否崩溃、是谁干的、实例整体是否健康] → [每条结论标 Measured（附来源）/ Inferred / Withdrawn；查不到写 not captured：为什么]。

输出：[固定格式私信：标题（严重度+节点+时间）→ 一句话影响 → What we measured（2–4 条带数字）→ Who → Why → Do（精确 T-SQL 与执行人，或 Nothing to run）→ Watch]；[CRITICAL <3,500 字符；其余不发声]。

禁令（写进代码，不只写进提示词）：[模型永不持有密钥] [永不向 SQL 写] [永不主动发频道消息] [只私信白名单里的三人，或在 #db-alerts 的告警帖下回帖]。

收尾：[更新状态文件水位；每 tick 一行日志 ok result=quiet|dm_sent cost_usd=0.21]。

```

中国读者怎么迁移

这是一套企业 DBA 团队的打法，不是个人读者的周末项目：前提是你已经在管 SQL Server 集群、有 Slack、有 Windows 服务器。个人读者能直接抄走的是三条原则：把监控做成“每次从零开始的 tick”而不是长驻进程；把“能联系谁、能回哪里”写进代码而不是只写进提示词；每条结论标 Measured / Inferred / Withdrawn，查不到就明说。国内用钉钉/企业微信告警、MySQL 或 PostgreSQL 的团队，规则骨架同样适用，工具面要换成对应的只读诊断接口。
