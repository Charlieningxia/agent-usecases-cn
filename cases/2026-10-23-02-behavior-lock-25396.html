一句话

一个用 Claude Code 维护自己代码库的智能体，在动手做一次大型重构之前，先让智能体写了 25,396 个“行为锁”测试——不问代码对不对，只问“和昨天做的是不是一模一样”，连 bug 也原样钉住。

原作者怎么做的

  1. 先缩小目标：重构前删掉生产代码没调用的导出函数、类型、文件和两个无用依赖，共 1,358 行——不用保护的代码先清掉。
  2. 让智能体先写 case list 再写测试：每个 case 有编号，每个测试标题以编号开头；769 个文件镜像源码树；25,310 个测试带编号。
  3. 行为锁的规则：期望值来自“跑今天的代码”，不是来自设计文档；测试与代码不一致时，钉住代码的行为，分歧单独报给主人裁决——有一个 bug（回复合规检查误判版本号“2.1”为测量数字）被故意钉住，等主人拍板。
  4. 每个锁文件进沙盒：Jest 的 setupFilesAfterEach 把工作目录搬进临时目录，HOME 与 os.homedir() 指向沙盒；repo 内文件写、repo 内子进程工作目录、fetch/http/https（localhost 除外）全禁；名字像 secrets 的环境变量（TOKEN、PASSWORD、COOKIE 等）全删；TZ 固定。这个沙盒在建成过程中自己漏了 6 次才补牢（比如只改 HOME 没改 os.homedir() 导致测试改写了真实缓存）。
  5. 锁的提交纪律写进 coding rules 一行：改动非预期→修代码；改动是预期的→改期望值并在 commit message 里写原因。至今 6 个 commit 改过期望值。
  6. 写锁过程抓出 3 个 bug：DM 回复的“不再回复”消息绕过了全部三道发送前检查（修好后 5 个真实待办被正确拦截）、年终目标缺 follower 指标时周报崩溃、生成标签缺空格。
  7. 覆盖率 64.6%→99.1% 后，主人要求“低于 100% 必须有主人批准的理由”，于是智能体把 235 处测不到的代码写成 222 行理由清单——截至 10 月 13 日一行都没被批准。

结果

  • 规模：769 文件、25,396 测试全过，504,824 行测试代码保护 162,385 行源码（已实现，作者自述，终端截图）
  • 覆盖率：语句 64.6%→99.1%，分支 59.2%→98.3%（已实现，作者自述）
  • 抓 bug：写锁过程发现并修复 3 个真实 bug；锁落地后 6 个 commit 因改动行为被拦截并写明原因（已实现，作者自述）
  • 成本：全量跑 8 分 44 秒（10 核高负载机器，作者声明按上限理解）；沙盒补 6 个洞、50 万行测试代码的阅读成本是真实代价

提示词结构

（按原文做法还原的指令结构，非原文逐字提示词）

```

任务：在[重构目标]动手前，先建 behavior-lock。

第 1 步（缩小目标）：删掉生产代码未调用的导出/类型/文件与无用依赖，减少要保护的面积。

第 2 步（case list）：为每个要锁的行为写一行 case：[编号] + 一句话行为描述；先出文档，再写测试。

第 3 步（锁的语义）：期望值 = 跑今天代码的结果；测试与代码不一致时，钉住代码，分歧报给[主人]裁决。

第 4 步（沙盒）：每个锁文件跑在隔离环境——禁写 repo、禁网（localhost 除外）、删 secrets 类环境变量、固定 TZ；违反隔离的操作必须让测试失败。

第 5 步（提交纪律）：改动非预期→修代码；改动是预期的→改期望值并在 commit message 写原因。

验收：覆盖率低于 100% 的每一处都要有一行主人批准的理由。

```

中国读者怎么迁移

思路与工具无关：Codex、通义灵码、文心快码都能搬。关键是三件小事——“期望值来自今天的代码而非设计文档”（这叫 characterization test，老方法新用）、沙盒清单（禁写、禁网、删 secrets 三条最值钱）、提交纪律那一行规则。先在自己项目的核心模块做缩小版（几十个 case），别一上来全仓 25,396 个。

风险与限制

  • 作者只有 handle 署名（Rulestack），个人全名未给出——按本站博客署名先例（Devaland、mewset）列入推荐，发布前如能补到实名应补。
