让智能体把需求写成一叠已评审的 PR：每 PR 实测成本约 $2.42

作者/出处：Seb Wilgosz

成本：插件免费（MIT）；按 API 标价每 PR 约 $2.18–$2.58（Opus 评审 $0.95 + Sonnet 编排 $0.71 + 构建/验证/修复 $0.76）；订阅用户按用量额度计，不直接付美元 · 耗时：安装约 30 分钟；跑一次评审看仓库大小

一句话

Seb Wilgosz 写了一个免费 Claude Code 插件 Executor：你给一份需求文档，它自动拆成特性、并行写代码、每个 PR 都经过构建、评审、验证、修复再交给你合并——他把 11 次真实构建的账单摊开：一个已评审的 PR 平均约 $2.42，其中 Opus 只做评审、其余全走便宜的 Sonnet。

原作者怎么做的

  1. 先给 spec：用 /executor:spec 把笔记、RFC、Issue 或 Notion 文档写成需求文档；需求太薄时插件会先提问，每个问题附建议答案。
  2. 人工批计划：插件把 spec 拆成特性和 PR 栈、写出检查清单，你先批计划；共享地基（schema、鉴权、骨架）单独先建一个 PR。
  3. 并行构建：每个栈一个 Sonnet builder，各自在独立 worktree 里工作；先按 spec 写测试再写代码，一个步骤一个 commit，代码不能悄悄改写“完成”的定义。
  4. 逐 PR 评审：每个 PR 先跑构建、lint 和测试（在一次性 worktree 里，不动你的工作区），再由一个 Opus reviewer 按 spec、测试、安全和你的仓库规范审 diff；Critical 问题不直接动手修。
  5. 验证后再修：每个 Critical 发现单独派一个 Sonnet verifier，任务只有一个——证伪它；315 次验证运行至今推翻 18 项、降级 47 项；只有被证实的 bug 才派 fixer 写“先写失败测试、再修代码”，最多 3 轮。
  6. 合并权在人：每个 PR 都是草稿 PR，排成 GitHub 栈；最后给出一块汇总——哪些能合、哪些有未决问题、按什么顺序合；合并由你点。

结果

  • 仅测试（实测成本账本，作者自述、README 逐项列出）：当前版本（0.13.x）一个已评审的 PR 成本 $2.18–$2.58；4 个 PR 的一次构建总计 $9.69，合 $2.42/PR；另三次单 PR 构建分别为 $2.53、$2.58、$2.18。
  • 角色拆分（4-PR 构建）：评审（Opus）$0.95/PR；编排（Sonnet）$0.71/PR；构建、验证、修复（Sonnet）$0.76/PR。
  • 版本演进：0.10.0 时 $1.87/PR（9 个 PR）；0.12.0 时 $1.43/PR（测试改走 CI）；0.13.0 时 $2.33–$3.13/PR；0.13.x 把编排从 Opus 换成 Sonnet 后降到 $2.18–$2.58。
  • 验证机制实测：315 次 verifier 运行，推翻 18 项发现、降级 47 项——这是“评审发现先证伪再修”的实际运转数，不是省钱数。
  • 这不是省钱结果：作者没说替他省了多少钱或多少小时，只给出了“一个已评审 PR 值多少钱”的实测账本；读者用它能回答“把需求交给智能体做 PR，预算该怎么算”。

提示词结构

（按原文工作流转写；原文为插件命令与规则，非大段提示词照抄）

```

/executor:spec [需求笔记 / RFC / Issue / Notion 链接]

→ 需求太薄时先回答插件的提问（每个问题有建议答案）

人工批计划：拆成的特性、PR 栈、检查清单先由你确认

/executor:build [spec 路径或文本]

→ 先写地基 PR → 各栈并行构建 → 每个 PR：构建+测试 → Opus 评审

→ Critical 发现 → verifier 证伪 → 证实后 fixer 修（最多 3 轮）→ 草稿 PR 入栈

/executor:review [PR 号或分支] # 只评审不构建，也能审人工写的 PR

/executor:status # 看哪些栈现在能合

```

关键不在话术，在四条结构：① Opus 只做判断（评审），其余全走 Sonnet——这是成本账本成立的前提；② 确定性工作（开 PR、等 CI、贴状态）用脚本做，不占模型轮次；③ 测试先于代码、按 spec 写，构建者改不了“完成”的定义；④ 每个 Critical 发现先证伪再修，修之前必须先写失败测试。

中国读者怎么迁移

这套做法不依赖 Executor 本身：任何支持子智能体/并行任务的编程助手都能复现“评审 Opus + 其余 Sonnet”的分工与“先证伪再修”的流程，关键是把“每 PR 成本”当成预算指标来记——跑 3–5 个 PR 就能算出自己仓库的单价，再决定哪些需求值得交给智能体。国内读者注意：Claude Code 与 gh-stack 的可用性、API 计价与订阅额度因地区与套餐而异，先用一个小需求（1–2 个 PR）实测自己的单价再铺开；订阅用户付的是用量额度而非美元，角色间的成本比例仍可参考。

  • 作者自推，须显眼说明：Executor 是作者本人的免费插件（MIT 开源），README 首页即挂 5 天免费邮件课与个人 newsletter 引流；本案价值在“实测成本账本”，不是第三方独立评测。
  • 样本小：作者原文自承只覆盖 11 次构建、每次 1–4 个 PR，且多为 Markdown 与 shell 仓库；你的仓库类型不同，单价会不同；小构建的单价看起来更贵（读 spec 与做计划的成本 1 个 PR 和 9 个 PR 差不多）。
  • 成本口径：按 API 标价（Opus $4/$20、Sonnet $2/$10 每百万 token，缓存读 $0.20）计算；订阅用户按用量额度计，美元数不直接适用；最便宜的一次构建（$2.18）是因为没发现 bug、没跑验证与修复轮次——bug 越多，每 PR 越贵。
  • 结果口径：只有成本账本与验证运行数，无省钱、省时总数；不要写成“省了多少钱”。
  • 门槛与前置：需 Claude Code、GitHub CLI（已登录）、gh-stack 扩展与 jq（可选）；PR 栈功能要求仓库开启 stacked PR；插件从不合并、不改测试、不碰 fork 的 PR，合并始终由人点。
