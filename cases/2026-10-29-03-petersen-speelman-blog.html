一句话

想让智能体替你建站，先别急着让它写代码：作者用 3 小时预算、17 条事先谈妥的决定与两道检查，建好一个“Markdown 是唯一事实来源、智能体只负责把每页手写成 HTML”的个人博客——最值钱的不是建站本身，是那道“一个词都不能改”的保真门禁。

原作者怎么做的

  1. 计划先行：动工前先让 Claude 用 grill-me skill 反复追问，直到谈妥 17 条决定（每个都写明放弃了哪个替代方案），形成 PLAN.md；计划分 8 个阶段、列出智能体不许做的事，其中一处是检查点——智能体必须停下等作者选设计。
  2. 定四行核心架构：Markdown 是每篇文章的事实来源；智能体按设计简报手写每页 HTML，不用静态站点生成器、不套模板；RSS、sitemap 与保真门禁这类“必须精确”的东西用纯 Ruby 脚本；Cloudflare 直接 serve 提交的文件，部署无构建步骤、无 API key。
  3. 给文字装保真门禁：计划规定智能体绝不改动、增删、重排作者原文；作者不信这条指令——门禁把 Markdown 渲染出来，从智能体生成的 HTML 里抽出正文，逐块比对标题、段落、列表与每一行代码（空白可变，其余一律不许变）； curly 引号变直引号、少一行代码都会失败并打印 diff 告诉智能体改哪里。门禁挂在 pre-commit hook 上，智能体与作者本人都无法提交改动原文的页面；端到端测试里它拦下过一次“一个词不同”的提交。首页介绍后来也纳入同一门禁（改版会重写首页，故介绍单独成 Markdown 文件）。
  4. 设计走“3 + 1”：智能体先出三个方向（编辑衬线风、工程笔记本风、钴蓝珊瑚柠檬黄的大声风）各带首页与样例文章；作者要了第四个（笔记本 + 大声风结合），最后还是选了最初的笔记本风；两个硬条件是移动优先与无障碍——闪烁光标 4 次后停止、装饰性 shell 提示对读屏器隐藏。
  5. 补第二道检查：保真门禁只能证明“字没错”，证明不了“读起来对不对”——手机与桌面宽度的截图找出 8 个纯文本检查看不出的问题，作者列出 4 个：段落无间距（一条 CSS 规则优先级压过另一条）、作者名在手机上溢出屏幕、字体缺不间断连字符字形、代码连字把 #{ 合成一个字形导致屏上代码与原文不符。于是智能体又写了 bin/check-pages：跑 axe-core 无障碍检查（亮暗两种模式）、查三档宽度的横向滚动、存截图要求智能体交活前自己先看；计划没要这件东西，作者说现在“几乎比仓库里任何东西都更想留着它”。智能体在构建日志里自认该在第 2 阶段而非第 5 阶段建截图检查，作者同意，并引用自己另一篇工具文章的观点：工具只有被智能体读了输出才有用。
  6. 上线：Cloudflare 由作者自己手工配（简单到可以手配），智能体逐项从旁核对。

设计流程：[3 个方向各带首页与样例] + [1 个结合版]，硬条件 [移动优先] + [无障碍]，选完再让智能体逐项改。

中国读者怎么迁移

想用智能体建个人站、作品集、文档站的读者可以直接抄这套“计划 + 两道检查”：先花时间把决定谈妥写进 PLAN.md（尤其“智能体不许动原文”这类规则），再让它动手；保真门禁的思想不限于博客——凡是“智能体不能改我原文”的场景（简历、投稿、合同模板）都可以用“渲染原文 vs 抽出生成物逐块比对 + pre-commit 拦截”照搬；截图检查则是第二道防线，适合一切“字对了但排版错了”的页面。国内读者若用 Vercel/Cloudflare Pages/对象存储静态托管，同样可以做到无构建步骤部署；但要注意：作者的“手写每页 HTML”是刻意选择，换成模板生成器会失去“每篇可单独设计”的自由，换之前先想清楚自己要不要这份自由。
