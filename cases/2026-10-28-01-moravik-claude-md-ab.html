让智能体写代码前先砍指令文件：13 次 A/B 实测，33KB 的 CLAUDE.md 没买到可测量的质量

作者/出处：Štefan Moravík
原文：https://www.flowhunt.io/blog/claude-md-ab-test-ai-coding-agent-instructions/
日期：2026-10-06（约，页面未印固定发布日；实测为 2026-10-05 的 13 次 headless 运行） · 工具：Claude Code 2.1.289、 Opus 5.5（主模型）、 Sonnet 5.5（子智能体）、 GitHub CI
成本：实验按 API 价目计：胜出组单次均值 $6.68，完整流水线组 $11.49；作者本人付订阅费，实付不是这个数（订阅用户照搬时以套餐为准） · 耗时：照搬“同一 issue 跑多组 + 双盲评审”的方法约半天搭架子；单次运行 21–45 分钟

速览卡

  • 分类：编程搭建
  • 结果：同一真实 issue（新用户定时邮件序列）跑 13 次、7 组指令配置、26 份双盲评审：33KB CLAUDE.md + 10 技能 + 流水线提示词组单次均值 $11.49、有 blocker；8KB CLAUDE.md + 3 技能 + Sonnet 子智能体 + 一段 plain 提示词组单次均值 $6.68、零 blocker、严重问题最少
  • 状态：已实现（作者实验实测；单 issue 单仓库）
  • 成本：按 API 价目计，胜出组比完整组便宜约 42%
  • 耗时：搭 A/B 架子约半天；胜出组单次约 21 分钟、完整组约 45 分钟

一句话

指令文件越攒越长，不等于智能体写得越好：作者把自家 33KB 的 CLAUDE.md 和 10 个技能、流水线提示词拆成 7 组，对同一个真实需求跑 13 次、请两个“盲眼”模型评审打分——结果是文件最全的那组又贵又有 blocker，反而是砍到 8KB、只留 3 个技能的那组最便宜、严重问题最少。

原作者怎么做的

  1. 起因：FlowHunt 单体仓的根 CLAUDE.md 攒到 33KB（构建命令、测试节奏、代码风格、架构、关键路径、安全、权限与点数规则、两个智能体入口、issue 与 PR 规范）+ 10 个技能 + 一条 CI 流水线（打标签 → 分流 → 写计划 → 读计划再写代码，每步都有长系统提示词）。每条都是某次智能体犯错后补的，但没人问过“还起不起作用”——而 CLAUDE.md 每会话、每轮都要重读重算，等于每轮都在交税。
  2. 定一个真实任务：新用户定时邮件序列（管理员定“第 0 天欢迎、第 5 天试用到期提醒”等步骤，后台任务按天发、用户付费后停售、发售前创建的账号跳过；要 migration、仓储层、服务层、Celery 定时任务、REST 端点、MCP 工具、11 语言控制台 UI），是“现实的一周功能”，且有几个容易漏的边界情况。
  3. 跑 7 组对照（13 次 headless Claude Code，Opus 5.5 主模型，architect 技能分流处用 Sonnet 5.5 子智能体；每组从同一提交起步、各自独立 clone 与数据库、脚本把提交推成 draft PR、把 CI 结果喂回会话最多 3 轮）：

- A：完整 33KB + 10 技能 + 流水线提示词（先计划后实现），2 次；

- B：完整文件 + 技能 + plain 提示词，3 次；

- C：无 CLAUDE.md、无技能、plain 提示词，2 次；

- D：完整文件 + architect 技能 + plain 提示词，2 次；

- E：8KB 文件 + 3 技能 + 流水线提示词，1 次；

- F：5.5KB 文件、无技能、plain 提示词，1 次；

- G：8KB 文件 + 3 技能（architect、grain-ponytail、unslop）+ plain 提示词，2 次。

  1. 双盲评审：每份结果交两个 Opus 评审，只看到字母编号、diff、仓库与 issue，按同一 rubric（正确性、验收标准、贴合度、私有字段与隐藏状态、过度工程、安全与权限、测试、迁移）列出“批准前必须改的项”，分 blocker/major/minor/nit；评审能读仓库、不能跑代码；每组结果按评审取均值。
  2. 按结果改自家流程：33KB CLAUDE.md 缩成 12KB AGENTS.md（Codex 也读，CLAUDE.md 只 import 它），只留“模型从代码里推不出来的规则”（哪些路径关键、两个智能体入口必须同步）；流水线里的计划阶段直接砍掉，分流后直通实现阶段，提示词缩成 6 步；architect 技能加“边界情况表”（每条验收标准、它依赖的状态随时间变化会怎样、定下来的行为）与 brief 里的 Tests 字段。

结果

  • 胜出组 G：单次 $5.96 与 $7.39（均值 $6.68），约 21 分钟，零 blocker、每评审 1.5 与 0.5 个 major（已实现，作者实验）
  • 完整流水线组 A：单次 $11.12 与 $11.85（均值 $11.49），约 45 分钟，主会话 144–172 轮、2400–2800 万输入 token；G 为 79–95 轮、1300–1600 万输入 token，另约 60 轮交给 Sonnet 子智能体（已实现，作者实验）
  • 33KB 文件没买到质量：完整文件组 B 每评审 2.0 个 major，与“无文件无技能”组 C 相同；5.5KB 无技能组 F 为 1.0 个（已实现，作者实验）
  • 计划阶段反而有害：A 与 E 两组（先计划后实现）比各自的 plain 提示词双胞胎（B、G）都贵，且 26 份评审里的 5 个 blocker 有 4 个出自这两组（已实现，作者实验）
  • 附带发现：完全不给指令也不是最便宜——C 组两次 $7.32 与 $15.58，贵的那次还 CI 失败、写了全场最大 diff；F 组写了 1601 行产品代码，并不比完整组便宜（已实现，作者实验）

提示词结构

（按原文做法还原的 A/B 骨架，非原文逐字提示词）

```

先定一个真实任务：[自己 backlog 里的一周功能]，必须有 [容易漏的边界情况]，不要用玩具任务。

同一任务跑多组：[完整指令文件] vs [砍掉后的文件] vs [无文件] vs [有/无计划阶段]，每组从 [同一提交] 起步、[独立 clone 与数据库]、[真实 CI 跑 3 轮以内]。

评审要盲：[只给编号、diff、仓库与 issue]，按 [正确性/验收标准/贴合度/隐藏状态/安全/测试] 分级列出必须改的项；评审能读代码、不能跑代码。

留的指令只留三类：[改写工作方式的]（谁写代码、切片怎么写 brief、抄哪个现成模式）+ [模型从代码推不出来的]（关键路径、双入口同步）+ [边界情况表：验收标准 × 状态随时间变化 × 定下来的行为 + 对应测试]。

砍的指令是两类：[模型本来就会的]（命名规范、架构复述）+ [给自己看的计划]（实现会话会把计划当外部指令照单全收、错了也跟）。

```

中国读者怎么迁移

自己仓库的 CLAUDE.md / AGENTS.md 超过 10KB 的读者可以直接抄这套 A/B：先别全盘删——挑 backlog 里一个中等功能，跑“现在的文件”与“砍到只剩命令、测试节奏、关键路径、双入口同步规则”两组，各跑 2 次、请同事或另一个模型盲评严重问题数与单次成本，再决定留什么。作者的教训对国内团队同样适用：计划文档是写给“另一个人”看的才值钱——主模型给自己写的计划，不如让它在要动手的会话里自己规划；但主模型交给便宜子智能体的切片，必须写成“目标、文件、照抄的模式、边界情况、要写的测试”齐全的 brief。

风险与限制

  • 单 issue 单仓库：13 次、每组 1–3 次，作者自承单组均值较 noisy；C 组两次成本 $7.32 与 $15.58 的落差就是例子——结论看的是“两组方向一致的大差距”，不是精确数字。
  • 成本是 API 价目、不是账单：作者本人付订阅费，total_cost_usd 只是工作量度量；订阅用户抄的是“相对便宜约 42%”这个方向，不是 $6.68 这个绝对数。
  • 评审也是模型：两个 Opus 评审按同一 rubric 打分、且不能跑代码；作者用“确定性 CI + 盲评”双轨对冲，但评审主观性仍在。
  • 胜出组也有代价：G 组过度工程项每评审 2.5 条、高于完整组的 0–1.0 条；作者自认“严重问题少、啰嗦多”是可接受的 trade-off，照搬时要自己权衡。
  • 改动当时还在评审中：原文写明“仓库改动在写本文时还在 review”，即 33KB→12KB 与砍计划阶段的落地效果尚未经生产验证；引用时要把“实验结论”与“落地效果”分开。
  • 与已发布案例的边界：本站已有档位基准（Ivanchenko 5 档 60 次）、token 分工实测；这篇测的是“指令文件本身值不值”，问题不同——它不改模型档位、不改分工，只动指令。
